# NBR e-Mushak sandbox harness

> Step-by-step procedure for validating `NbrReceiptServiceProduction` against a
> tenant's NBR sandbox credentials. Designed to be runnable by a deployment
> engineer with a fresh `Nbr.MerchantToken` + `Nbr.SigningKey` (PEM) in hand.

## What we ship

* [NbrReceiptServiceProduction](../src/CanteenManagementSystem.Infrastructure/Receipts/NbrReceiptService.Production.cs)
  — full HTTP plumbing: builds the Mushak 6.3 XML envelope, signs it RSA-SHA256,
  POSTs to `Nbr.GatewayBaseUrl/submit` with `Authorization: Bearer {token}` +
  `X-Signature: {base64-sig}`, parses the response for an FRN.
* [INbrReceiptService](../platform/Platform.Application/Abstractions/Receipts/INbrReceiptService.cs)
  — the interface every site code calls. Today's DI binds the stub; flipping
  one line in `DependencyInjection.cs` swaps in the production class.
* This harness — the manual "did the wire-up survive contact with NBR"
  procedure.

## Prerequisites

| Item | Where it comes from |
|---|---|
| `Nbr.Bin` | NBR business registration certificate. Pre-existing for the tenant. |
| `Nbr.MerchantToken` | NBR sandbox onboarding email. |
| `Nbr.SigningKey` | 2048-bit RSA private key in PEM. Generated by the tenant, public half registered with NBR. |
| `Nbr.GatewayBaseUrl` | Sandbox URL from NBR (e.g. `https://emushak-sbox.nbr.gov.bd/api/v1`). |

## Step-by-step

### 1. Set tenant settings

```sql
-- Replace <CLIENTID> with the tenant's ClientId
INSERT INTO CanteenTenantSettings (ClientId, [Key], Value, IsSecret)
VALUES
    (<CLIENTID>, 'Nbr.Enabled',         'true',                                     0),
    (<CLIENTID>, 'Nbr.Bin',             '<your BIN>',                               0),
    (<CLIENTID>, 'Nbr.MerchantToken',   '<sandbox token>',                          1),
    (<CLIENTID>, 'Nbr.SigningKey',      '<PEM private key>',                        1),
    (<CLIENTID>, 'Nbr.GatewayBaseUrl',  'https://emushak-sbox.nbr.gov.bd/api/v1',   0);
```

### 2. Switch DI to the production class

`src/CanteenManagementSystem.Infrastructure/DependencyInjection.cs` already
registers `StubNbrReceiptService`. For sandbox testing only — locally — change:

```csharp
services.AddScoped<INbrReceiptService, StubNbrReceiptService>();
```

to:

```csharp
services.AddScoped<INbrReceiptService, NbrReceiptServiceProduction>();
```

Restart the app.

### 3. Place a test order

Either through the kiosk / counter flow, or via the API:

```bash
curl -X POST http://localhost:8080/api/v1/orders \
  -H "Content-Type: application/json" \
  -H "X-App-Key: ..." -H "X-App-Signature: ..." -H "X-App-Timestamp: ..." \
  -d '{ "userId":"STUD-001", "userType":"Student", "items":[{ "dailyMenuId":1, "foodItemId":1, "quantity":1 }] }'
```

Note the returned `orderId` — e.g. `42`.

### 4. Trigger an NBR submission

```bash
curl -X POST http://localhost:8080/admin/receipts/nbr/submit/42 \
  -H "Cookie: <PlatformCookie session>"   # or use Bearer JWT
```

Expected response:

```json
{
  "frn":         "FRN-2026-06-05-000123",
  "verifyUrl":   "https://emushak-sbox.nbr.gov.bd/api/v1/verify?frn=FRN-2026-06-05-000123",
  "submittedAt": "2026-06-05T11:23:04Z",
  "rawResponse": "{...}"
}
```

### 5. Validate via NBR verify

Open the `verifyUrl` in a browser — NBR's portal will render the receipt back
with stamp confirmation. If the FRN doesn't render, the most common causes are:

| Failure | Fix |
|---|---|
| 401 Unauthorized | `Nbr.MerchantToken` is wrong / expired. Get a fresh one from NBR. |
| 400 BadRequest + signature error | `Nbr.SigningKey` is invalid PEM or the public half hasn't been registered with NBR. |
| 422 envelope schema | `Nbr.Bin` doesn't match the BIN encoded in the token. |
| 500 | Sandbox is down — retry in 15 minutes. |
| 200 but `frn` parses as `FRN-UNKNOWN-…` | The response shape changed; update `TryParseFrn` in `NbrReceiptServiceProduction.cs`. |

### 6. Capture the FRN on the order

Once the verify works, wire the FRN onto the order:

```csharp
order.NbrFrn        = result.Frn;
order.NbrSubmittedAt= result.SubmittedAt;
await _uow.SaveChangesAsync();
```

(Currently the consumer call-site that calls `INbrReceiptService.SubmitAsync`
is a TODO. Add a hosted service or a hook on `MarkOrderDeliveredCommand` once
this harness round-trips successfully.)

### 7. Roll out per-tenant

Repeat steps 1–6 for each tenant that holds an NBR merchant token. The DI
registration only needs to change once per deployment; the production class
itself reads creds per-request from `ITenantSettings` so multi-tenant is
already correct.

## What's intentionally not in this codebase

* **Signature ceremony beyond RSA-SHA256** — NBR's spec mandates additional
  envelope hashing for some categories of merchants (food-service with
  intoxicating drinks, etc.). The shipped class covers the standard food-service
  shape; extend the envelope build per the NBR onboarding pack if your tenant
  falls under a special category.
* **A live integration test in CI** — would require shipping sandbox creds in
  the repo, which is explicitly forbidden by [docs/Security.md](Security.md).
  Run this harness manually before deploying changes that touch
  `NbrReceiptServiceProduction.cs`.
